# Targeted security review: payments, tenancy and operations

Scope: the money paths (TanyMotos bookings, TanyEats orders, shared refunds), the cron and webhook entry points, and the code added for
this release. Not a full audit. Evidence is in the tests named in brackets. Nothing here is a claim of absolute security.

## Found and fixed in this release

| # | Finding | Fix | Evidence |
|---|---|---|---|
| S1 | **Payment details in logs.** A failed database statement produces `Failed query: <sql> params: <values>`; several payment, webhook and cron paths logged `error.message`, so buyer names, phone ciphertext and payment ids would reach the Workers logs and `cron_runs.result`. Reproduced: a 579-character message contained all three. | `lib/core/safe-error.ts` keeps the SQLSTATE and driver reason, drops every value. Applied to the webhook, booking confirmation, refund, cron and video-queue paths. | `tests/safe-error.test.ts`; the lead-failure test asserts the real webhook/confirm logs contain none of the buyer's or payment's values (fails if the raw message is restored) |
| S2 | **A genuine second payment was ignored.** A second, different captured payment on an already-paid Motors booking was only counted; on an Eats order it was silently ignored. The buyer stayed charged twice. | Refunded once through the idempotent wrapper (refund key = that payment's own id), audited as `payment.duplicate_refunded`, retried by Razorpay if it fails. | motors and payment-events integration tests (burst of duplicates = one refund; failure = 500 then one refund) |
| S3 | **Manual refunds were not attributable.** Neither the dealer's booking refund nor an Eats staff cancel-with-refund recorded who did it. | `payment.refund` audit entries with the acting user (`AdminSession.userId` added). The Motors entry commits in the same transaction as the refund intent. | motors integration test (two simultaneous clicks = one refund, one audit entry, actor recorded) |
| S4 | **Cross-tenant package id** (F1): a trip could store another business's package id for any non-package trip type. | Ownership is checked wherever the request is built (public and operator paths), for every trip type; foreign and unknown ids are refused identically. | `tests/cabs/booking-actions.integration.test.ts` (fails without the check) |
| S5 | **Captured payments that matched nothing left no trace** on the `payment.captured` path, and repeatedly failing webhooks were not counted. | `razorpay_webhook_unmatched{reason=no_order}` and `razorpay_webhook_failed{event}` metrics. | `tests/core-payments.test.ts` |
| S7 | **Anyone on the team could refund.** Staff could refund a booking token or cancel-and-refund a paid online order. | `canRefund` (owner only) enforced in both server actions before anything is read or changed; malformed ids rejected; the page hides the button from staff. Team add/remove/reset are audited. | `tests/refund-authorization.integration.test.ts` (12 tests: staff, owner, another business's owner, forged ids, signed out; fails if either check is removed) |
| S8 | **Production could be deployed by default.** `pnpm run deploy` went straight to Cloudflare production with no check, and wrangler without `--env` silently targets production. | `scripts/deploy.ts` is now the only door: no default environment, key-mode / database / domain / worker-name / account checks, a typed confirmation and `--migrations-applied` for production, and **no default production secrets file**. | `tests/deploy-guard.test.ts` (28 tests, including the CLI end to end; it also found that Node itself swallows `--env-file`) |
| S9 | **Eats refund recovery depended on Razorpay's webhook retries** and gave a guest wording ("has been refunded") that was untrue while the refund was pending. | `retry-order-refunds` job: crashed claims, released late-payment refunds, polling pending refunds; stable refund key; attempt limit; final failures stop and are put in front of a person; the guest page says "is being refunded" until Razorpay says processed. | `tests/eats-refund-recovery.integration.test.ts` (17), `tests/cron-financial.integration.test.ts` |
| S10 | **Money that needed a person was only in logs and metrics.** | `payment_exceptions` (one row per problem, deduplicated, auto-closed when cleared) and `/super/payments` where a Tany team member reads what to do and resolves with a note, recorded with their email. | `tests/payment-exceptions-admin.integration.test.ts` |
| S11 | **A payment whose notification never arrived was invisible** (order cancelled, guest charged). | The scheduled jobs ask Razorpay (a read) whether a stale order or booking was paid, and apply it exactly as a webhook would; an outage changes nothing. | `tests/cron-financial.integration.test.ts` (Eats and Motors, 8 tests) |
| S6 | **Booking and stock races** (M1-M3, E2), the **aborted-transaction retry** (T1) and the **silent video queue failure** (V1). | See the release notes. | their integration tests, plus mutation checks |

## Checked and found sound

- **Webhook:** HMAC over the raw body, constant-time comparison; any error returns 500 so Razorpay retries; logs carry the event name and a sanitised reason only.
- **Cron entry:** header secret, constant-time comparison, a 1-hour slot window, `(job, slot)` lock; unreachable from tenant hosts.
- **No external API call inside an open database transaction**, anywhere in the changed code (the claim transactions, `placeOrderAtomically`, `cancelAndRestock` and the hold sweep are database statements only).
- **Refund amounts** come from our own rows (`booking.amount`, `order.total`), never from the request; checkout order amounts are fixed server-side.
- **Tenant scoping in new code:** every write after the initial order-id lookup goes through `scopedDb(row.dealerId)`. The only unscoped reads are the lookups a webhook must do before it knows the tenant (by the unique Razorpay order id) and the read-only cross-tenant counts in the cron job. 27 files import the raw client; none is in `app/` outside the already-audited auth/tenant layers.
- **RLS:** not introduced. No concrete risk was found that the existing scoped layer, the registry test and the new constraints cannot control.

## Open: decisions and lower-priority items (not release blockers unless you decide otherwise)

| Priority | Item | Detail / suggested action |
|---|---|---|
| P2 | **Encryption key.** One environment key; ciphertext carries a version tag (`v1`) but no key id, so rotation means re-encrypting every row and re-hashing the blind indexes behind unique indexes. Loss of the key loses the data. | Store the key in two places outside the repo; add a key id before the first rotation is ever needed. |
| P2 | **Tenant deletion, customer export, retention.** No tenant or customer deletion/export code was found; the audit log is append-only by design; the notification outbox has no retention. | Needed for DPDP; write the procedure before the first deletion request. |
| P3 | **Rate limits.** Booking creation is limited per phone number only (not per IP); booking confirmation and the webhook are limited only by their signatures. | Add a per-IP limit to booking creation. |
| P3 | **Webhook does not cross-check the payment amount** against the booking/order. Low risk: the Razorpay order amount is fixed server-side at creation. | Add a check when convenient. |
| P3 | **Cross-tenant references at database level.** Single-column foreign keys do not stop a code bug from referencing another tenant. | Later: `UNIQUE(dealer_id, id)` on `packages` plus a composite foreign key from `trips(dealer_id, package_id)`, created `NOT VALID` then validated. Do not mass-change existing keys without evidence. |
| P2 | **"Authorized administrators" is not modelled.** The data has two roles, `owner` and `staff`; refunds are owner-only. A middle role would need a new enum value, a migration and the team screens. | Only if a business asks for a manager who may refund. `canRefund` in `lib/core/permissions.ts` is the one place to change. |
| P2 | **Payment states are compared with Razorpay only for refunds and for orders/bookings that look unpaid.** There is no daily comparison of every captured payment against our records. | A nightly job listing Razorpay's captured payments for the day and matching them to bookings/orders would close the remaining gap. Worth doing once volume makes a manual check impractical. |
| P3 | **Payment exceptions page has no per-admin permissions.** Any Tany team member on the allow-list can resolve an item. | Fine for a small team; the resolver's email is recorded. |
| P3 | **Index builds are not `CONCURRENTLY`.** `0031`/`0032` build their indexes with a brief write lock; the tables are small today. | Use `CREATE INDEX CONCURRENTLY` (outside the migration transaction) if `trips` or `orders` are large when a future index is added. |
| P3 | **A test-fixture flaw found and fixed:** fixtures built unique codes from three random characters, so repeated runs on a database that keeps rows eventually collided and failed "sometimes". | Fixed with `tests/support/ids.ts`; verified over repeated runs and on a fresh database. |
